# PostgreSQL Skill

## Overview
PostgreSQL is an advanced open-source object-relational database system with over 35 years of active development. It supports SQL (relational) and JSON (non-relational) querying, making it the most feature-rich open-source RDBMS available. Use this skill for relational data storage requiring advanced features like JSONB, CTEs, window functions, partitioning, full-text search, and Row-Level Security.

**Minimum Version**: PostgreSQL 15+ (recommended: PostgreSQL 16)
**References**:
- [Official Documentation](https://www.postgresql.org/docs/current/)
- [PostgreSQL Wiki — Performance Optimization](https://wiki.postgresql.org/wiki/Performance_Optimization)
- [PostgreSQL Wiki — Don't Do This](https://wiki.postgresql.org/wiki/Don%27t_Do_This)

## Setup & Connection

### Docker (Development)
```bash
# PostgreSQL 16 with Alpine (minimal image)
docker run -d \
  --name postgres \
  -p 5432:5432 \
  -e POSTGRES_USER=appuser \
  -e POSTGRES_PASSWORD=secure_password_here \
  -e POSTGRES_DB=mydb \
  -e POSTGRES_INITDB_ARGS="--auth-host=scram-sha-256" \
  -v pgdata:/var/lib/postgresql/data \
  postgres:16-alpine

# Verify connection
docker exec -it postgres psql -U appuser -d mydb -c "SELECT version();"
```

### Connection String Formats
```bash
# Standard format (with SSL required for production)
postgresql://appuser:password@localhost:5432/mydb?sslmode=require

# Key-value format (for libpq-based clients)
host=localhost port=5432 dbname=mydb user=appuser password=password sslmode=require

# ❌ NEVER use sslmode=disable in production
# ❌ NEVER use the postgres superuser for application connections
```

### Connection Pooling (PgBouncer — MUST use in production)
```ini
# pgbouncer.ini — WHY: PostgreSQL forks a new process per connection (~10MB each).
# Without pooling, 200 connections = 2GB RAM just for connections.
[databases]
mydb = host=localhost port=5432 dbname=mydb

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432
auth_type = scram-sha-256
auth_file = /etc/pgbouncer/userlist.txt

# Pool mode: transaction (recommended) — connection returned after each transaction
pool_mode = transaction
default_pool_size = 25
max_client_conn = 200
max_db_connections = 50

# Reserve connections for admin
reserve_pool_size = 5
reserve_pool_timeout = 3
```

## Schema Design

### Standard Table Pattern (Following Database Rules)
```sql
-- ✅ REQUIRED: UUID primary keys, audit columns, soft delete, constraints
CREATE EXTENSION IF NOT EXISTS "pgcrypto";

CREATE TABLE users (
    -- Primary key: UUID v4 generated by PostgreSQL
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    -- Business fields with appropriate constraints
    email VARCHAR(255) NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    first_name VARCHAR(100) NOT NULL,
    last_name VARCHAR(100) NOT NULL,
    phone VARCHAR(20),
    avatar_url TEXT,

    -- Status & flags
    is_active BOOLEAN NOT NULL DEFAULT true,
    email_verified_at TIMESTAMPTZ,

    -- Multi-tenancy support
    tenant_id UUID NOT NULL REFERENCES tenants(id),

    -- Audit columns (REQUIRED on every table)
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    created_by UUID REFERENCES users(id),
    updated_by UUID REFERENCES users(id),

    -- Soft delete (REQUIRED — never use hard DELETE on business data)
    deleted_at TIMESTAMPTZ DEFAULT NULL,

    -- Constraints
    CONSTRAINT uq_users_email UNIQUE (email),
    CONSTRAINT ck_users_email_format CHECK (email ~* '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Z]{2,}$')
);

-- Indexes (design indexes BEFORE data grows large)
CREATE INDEX idx_users_email_active ON users (email) WHERE deleted_at IS NULL;
CREATE INDEX idx_users_tenant ON users (tenant_id) WHERE deleted_at IS NULL;
CREATE INDEX idx_users_name ON users (last_name, first_name) WHERE deleted_at IS NULL;
CREATE INDEX idx_users_created ON users (created_at DESC);

-- Auto-update updated_at trigger
CREATE OR REPLACE FUNCTION update_updated_at()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_users_updated_at
    BEFORE UPDATE ON users
    FOR EACH ROW
    EXECUTE FUNCTION update_updated_at();

-- Add comment for documentation
COMMENT ON TABLE users IS 'Application users with soft delete and audit trail';
COMMENT ON COLUMN users.deleted_at IS 'Soft delete timestamp — NULL means active';
```

### Anti-Patterns (❌ DON'T do this)
```sql
-- ❌ NEVER: Use SERIAL/BIGSERIAL for primary keys (use UUID instead)
-- WHY: Sequential IDs leak information (user count, creation order) and cause
-- conflicts in distributed systems.
CREATE TABLE bad_users (
    id SERIAL PRIMARY KEY  -- ❌ Exposes user count, not merge-safe
);

-- ❌ NEVER: Store money as FLOAT/DOUBLE
-- WHY: Floating-point arithmetic causes rounding errors (0.1 + 0.2 ≠ 0.3)
CREATE TABLE bad_orders (
    total FLOAT  -- ❌ Will lose cents over time
);
-- ✅ CORRECT: Use NUMERIC or INTEGER (cents)
CREATE TABLE orders (
    total_cents INTEGER NOT NULL,  -- Store as cents: 9999 = $99.99
    -- OR
    total_amount NUMERIC(12, 2) NOT NULL  -- Fixed precision
);

-- ❌ NEVER: Use TEXT without constraints for structured data
-- ❌ NEVER: Create tables without audit columns (created_at, updated_at)
-- ❌ NEVER: Use ON DELETE CASCADE on business tables (use soft delete)
-- ❌ NEVER: Name constraints with auto-generated names (always name explicitly)
```

### Relationships Pattern
```sql
-- One-to-Many: User has many Orders
CREATE TABLE orders (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    order_number VARCHAR(20) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'pending'
        CHECK (status IN ('pending', 'confirmed', 'shipped', 'delivered', 'cancelled')),
    total_cents INTEGER NOT NULL CHECK (total_cents >= 0),
    currency CHAR(3) NOT NULL DEFAULT 'USD',
    notes TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    deleted_at TIMESTAMPTZ,
    CONSTRAINT uq_orders_number UNIQUE (order_number)
);

CREATE INDEX idx_orders_user ON orders (user_id) WHERE deleted_at IS NULL;
CREATE INDEX idx_orders_status ON orders (status) WHERE deleted_at IS NULL;

-- Many-to-Many: Users and Roles (junction table)
CREATE TABLE user_roles (
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role_id UUID NOT NULL REFERENCES roles(id) ON DELETE CASCADE,
    assigned_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    assigned_by UUID REFERENCES users(id),
    PRIMARY KEY (user_id, role_id)
);
```

## Advanced Features

### JSONB for Semi-Structured Data
```sql
-- WHY: JSONB is binary-stored, indexable, and queryable — perfect for
-- flexible metadata, user preferences, or API response caching.
ALTER TABLE products ADD COLUMN metadata JSONB NOT NULL DEFAULT '{}';

-- GIN index for containment queries (@>, ?, ?|, ?&)
CREATE INDEX idx_products_metadata ON products USING GIN (metadata);

-- GIN index for specific path (faster for known query patterns)
CREATE INDEX idx_products_brand ON products USING BTREE ((metadata->>'brand'));

-- ✅ Query examples
-- Exact key match
SELECT * FROM products WHERE metadata->>'brand' = 'Apple';

-- Containment (is this JSON a subset?)
SELECT * FROM products WHERE metadata @> '{"color": "red", "size": "L"}';

-- Key existence
SELECT * FROM products WHERE metadata ? 'warranty';

-- Nested path access
SELECT * FROM products WHERE metadata #>> '{specs,cpu,cores}' = '8';

-- Array contains value
SELECT * FROM products WHERE metadata->'tags' ? 'bestseller';

-- JSONB aggregation
SELECT
    metadata->>'category' AS category,
    COUNT(*) AS product_count,
    AVG((metadata->>'price')::numeric) AS avg_price
FROM products
WHERE deleted_at IS NULL
GROUP BY metadata->>'category'
ORDER BY product_count DESC;

-- ❌ DON'T: Store relational data in JSONB (normalize instead)
-- ❌ DON'T: Use JSON type (use JSONB — it's faster for reads and indexable)
-- ❌ DON'T: Store large documents (>1MB) in JSONB columns
```

### Common Table Expressions (CTEs)
```sql
-- WHY: CTEs improve readability and enable recursive queries.
-- PostgreSQL 12+ materializes CTEs only when beneficial (optimizer decides).

-- Example: Monthly revenue with growth percentage
WITH monthly_revenue AS (
    SELECT
        date_trunc('month', created_at) AS month,
        SUM(total_cents) / 100.0 AS revenue,
        COUNT(*) AS order_count
    FROM orders
    WHERE status = 'delivered' AND deleted_at IS NULL
    GROUP BY 1
),
with_growth AS (
    SELECT
        month,
        revenue,
        order_count,
        LAG(revenue) OVER (ORDER BY month) AS prev_revenue,
        revenue / NULLIF(LAG(revenue) OVER (ORDER BY month), 0) - 1 AS growth_rate
    FROM monthly_revenue
)
SELECT
    TO_CHAR(month, 'YYYY-MM') AS period,
    TO_CHAR(revenue, 'FM$999,999,999.00') AS revenue,
    order_count,
    COALESCE(ROUND(growth_rate * 100, 1) || '%', 'N/A') AS growth
FROM with_growth
ORDER BY month DESC
LIMIT 12;
```

### Recursive CTEs
```sql
-- WHY: Essential for tree/hierarchical data (org charts, categories, comments)
-- Example: Organization hierarchy
WITH RECURSIVE org_tree AS (
    -- Base case: top-level (no parent)
    SELECT id, name, parent_id, 1 AS depth, ARRAY[name] AS path
    FROM departments
    WHERE parent_id IS NULL

    UNION ALL

    -- Recursive case: children
    SELECT d.id, d.name, d.parent_id, ot.depth + 1, ot.path || d.name
    FROM departments d
    INNER JOIN org_tree ot ON d.parent_id = ot.id
    WHERE ot.depth < 10  -- Safety limit to prevent infinite loops
)
SELECT
    REPEAT('  ', depth - 1) || name AS department,
    depth,
    array_to_string(path, ' → ') AS full_path
FROM org_tree
ORDER BY path;

-- Output:
-- Engineering                    | 1 | Engineering
--   Backend                     | 2 | Engineering → Backend
--     API Team                  | 3 | Engineering → Backend → API Team
--   Frontend                    | 2 | Engineering → Frontend
```

### Window Functions
```sql
-- WHY: Window functions compute values across rows related to current row
-- WITHOUT collapsing rows (unlike GROUP BY).

-- Example 1: Rank employees by salary within department
SELECT
    name,
    department,
    salary,
    RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS dept_rank,
    DENSE_RANK() OVER (ORDER BY salary DESC) AS company_rank,
    PERCENT_RANK() OVER (PARTITION BY department ORDER BY salary) AS percentile
FROM employees
WHERE deleted_at IS NULL;

-- Example 2: Running total and moving average
SELECT
    date,
    daily_revenue,
    SUM(daily_revenue) OVER (ORDER BY date ROWS UNBOUNDED PRECEDING) AS running_total,
    AVG(daily_revenue) OVER (ORDER BY date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS moving_avg_7d
FROM daily_sales;

-- Example 3: Find gaps in sequences
SELECT
    order_number,
    LEAD(order_number) OVER (ORDER BY order_number) AS next_number,
    LEAD(order_number) OVER (ORDER BY order_number) - order_number AS gap
FROM orders
HAVING gap > 1;
```

### Row-Level Security (RLS)
```sql
-- WHY: RLS enforces data isolation at the database level — even if application
-- code has bugs, tenants can NEVER see each other's data.

-- Step 1: Enable RLS
ALTER TABLE projects ENABLE ROW LEVEL SECURITY;

-- Step 2: Force RLS even for table owners
ALTER TABLE projects FORCE ROW LEVEL SECURITY;

-- Step 3: Create policies
-- Policy for SELECT: users can only see their tenant's projects
CREATE POLICY tenant_select ON projects
    FOR SELECT
    USING (tenant_id = current_setting('app.current_tenant')::UUID);

-- Policy for INSERT: users can only insert into their tenant
CREATE POLICY tenant_insert ON projects
    FOR INSERT
    WITH CHECK (tenant_id = current_setting('app.current_tenant')::UUID);

-- Policy for UPDATE: same tenant + must be project owner or admin
CREATE POLICY tenant_update ON projects
    FOR UPDATE
    USING (tenant_id = current_setting('app.current_tenant')::UUID)
    WITH CHECK (tenant_id = current_setting('app.current_tenant')::UUID);

-- Policy for DELETE: same tenant + admin only
CREATE POLICY tenant_delete ON projects
    FOR DELETE
    USING (
        tenant_id = current_setting('app.current_tenant')::UUID
        AND current_setting('app.current_role') = 'admin'
    );

-- Step 4: Set context in application (per-request)
-- In your application middleware:
-- SET LOCAL app.current_tenant = 'tenant-uuid-here';
-- SET LOCAL app.current_role = 'admin';
-- (SET LOCAL is scoped to the current transaction)
```

### Full-Text Search
```sql
-- WHY: PostgreSQL's built-in FTS is powerful enough for most use cases,
-- eliminating the need for Elasticsearch in many scenarios.

-- Add tsvector column with trigger
ALTER TABLE articles ADD COLUMN search_vector tsvector;

CREATE INDEX idx_articles_search ON articles USING GIN (search_vector);

-- Auto-update search vector on INSERT/UPDATE
CREATE OR REPLACE FUNCTION articles_search_update() RETURNS TRIGGER AS $$
BEGIN
    NEW.search_vector :=
        setweight(to_tsvector('english', COALESCE(NEW.title, '')), 'A') ||
        setweight(to_tsvector('english', COALESCE(NEW.summary, '')), 'B') ||
        setweight(to_tsvector('english', COALESCE(NEW.body, '')), 'C');
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_articles_search
    BEFORE INSERT OR UPDATE OF title, summary, body ON articles
    FOR EACH ROW EXECUTE FUNCTION articles_search_update();

-- Search with ranking
SELECT
    id, title, summary,
    ts_rank_cd(search_vector, query) AS rank,
    ts_headline('english', body, query, 'MaxWords=50, MinWords=20, StartSel=<b>, StopSel=</b>') AS snippet
FROM articles, plainto_tsquery('english', 'postgresql performance tuning') AS query
WHERE search_vector @@ query
ORDER BY rank DESC
LIMIT 20;

-- Phrase search
SELECT * FROM articles
WHERE search_vector @@ phraseto_tsquery('english', 'database optimization');
```

### Partitioning
```sql
-- WHY: Partitioning improves query performance on very large tables (>100M rows)
-- by enabling partition pruning — queries only scan relevant partitions.

-- Range partitioning by date (most common)
CREATE TABLE events (
    id UUID NOT NULL DEFAULT gen_random_uuid(),
    event_type VARCHAR(50) NOT NULL,
    payload JSONB NOT NULL,
    user_id UUID NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
) PARTITION BY RANGE (created_at);

-- Create partitions (automate with pg_partman extension)
CREATE TABLE events_2026_q1 PARTITION OF events
    FOR VALUES FROM ('2026-01-01') TO ('2026-04-01');
CREATE TABLE events_2026_q2 PARTITION OF events
    FOR VALUES FROM ('2026-04-01') TO ('2026-07-01');
CREATE TABLE events_2026_q3 PARTITION OF events
    FOR VALUES FROM ('2026-07-01') TO ('2026-10-01');
CREATE TABLE events_2026_q4 PARTITION OF events
    FOR VALUES FROM ('2026-10-01') TO ('2027-01-01');

-- Default partition (catches data that doesn't match any partition)
CREATE TABLE events_default PARTITION OF events DEFAULT;

-- Indexes on partitioned tables are created on each partition
CREATE INDEX idx_events_user ON events (user_id);
CREATE INDEX idx_events_type ON events (event_type);

-- ❌ DON'T: Partition tables with fewer than 10M rows (overhead > benefit)
-- ❌ DON'T: Create too many partitions (>1000 increases planning time)
```

## Performance Tuning

### Query Analysis (ALWAYS do this before optimization)
```sql
-- EXPLAIN ANALYZE shows actual execution time and row counts
-- BUFFERS shows disk I/O (shared hit = cache, read = disk)
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT u.*, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON o.user_id = u.id AND o.deleted_at IS NULL
WHERE u.tenant_id = 'some-uuid' AND u.deleted_at IS NULL
GROUP BY u.id
ORDER BY u.created_at DESC
LIMIT 20;

-- Key things to look for in EXPLAIN output:
-- 1. Seq Scan on large tables → need an index
-- 2. Nested Loop with large outer table → consider Hash Join
-- 3. Sort with high cost → add index matching ORDER BY
-- 4. Rows estimated vs actual differ significantly → run ANALYZE
-- 5. Buffers read >> Buffers hit → insufficient shared_buffers
```

### Index Strategy
```sql
-- B-Tree (default) — equality and range queries
CREATE INDEX idx_users_email ON users (email);

-- Partial index — index only relevant rows (smaller, faster)
CREATE INDEX idx_orders_pending ON orders (created_at)
    WHERE status = 'pending' AND deleted_at IS NULL;

-- Composite index — order matters! Most selective column first
CREATE INDEX idx_orders_user_status ON orders (user_id, status);

-- Covering index (INCLUDE) — avoids heap lookup for common queries
CREATE INDEX idx_users_email_covering ON users (email)
    INCLUDE (first_name, last_name, is_active)
    WHERE deleted_at IS NULL;

-- GIN index — for JSONB, arrays, full-text search
CREATE INDEX idx_products_tags ON products USING GIN (tags);

-- GiST index — for geometric, range, and proximity queries
CREATE INDEX idx_locations_coords ON locations USING GIST (coordinates);

-- BRIN index — for naturally ordered data (timestamps, sequences)
-- Very small index size for large tables with correlated data
CREATE INDEX idx_events_created ON events USING BRIN (created_at);

-- ❌ DON'T: Index every column (write overhead)
-- ❌ DON'T: Create redundant indexes (a, b) already covers queries on (a)
-- ❌ DON'T: Index low-cardinality columns alone (boolean, status with 3 values)
```

### postgresql.conf Tuning
```ini
# Memory (adjust based on available RAM)
shared_buffers = 4GB              # 25% of total RAM (for 16GB server)
effective_cache_size = 12GB       # 75% of total RAM
work_mem = 64MB                   # RAM / max_connections / 4
maintenance_work_mem = 1GB        # For VACUUM, CREATE INDEX, etc.
huge_pages = try                  # Enable if OS supports it

# WAL (Write-Ahead Log)
wal_buffers = 64MB                # 1/32 of shared_buffers
checkpoint_completion_target = 0.9
max_wal_size = 4GB
min_wal_size = 1GB

# Planner
random_page_cost = 1.1            # For SSD (default 4.0 is for HDD)
effective_io_concurrency = 200    # For SSD
default_statistics_target = 200   # More accurate planner estimates

# Connections
max_connections = 100             # Keep low, use PgBouncer for pooling

# Logging
log_min_duration_statement = 500  # Log queries slower than 500ms
log_checkpoints = on
log_lock_waits = on
log_temp_files = 0                # Log all temp file usage
```

### Maintenance
```sql
-- VACUUM reclaims dead tuple space, ANALYZE updates statistics
-- PostgreSQL autovacuum handles this, but verify it's working:
SELECT
    schemaname, relname,
    n_dead_tup,
    n_live_tup,
    last_vacuum,
    last_autovacuum,
    last_analyze,
    last_autoanalyze
FROM pg_stat_user_tables
WHERE n_dead_tup > 1000
ORDER BY n_dead_tup DESC;

-- Force VACUUM ANALYZE on specific table after bulk operations
VACUUM (ANALYZE, VERBOSE) orders;

-- Identify bloated tables
SELECT
    tablename,
    pg_size_pretty(pg_total_relation_size(schemaname || '.' || tablename)) AS total_size,
    pg_size_pretty(pg_relation_size(schemaname || '.' || tablename)) AS table_size,
    pg_size_pretty(pg_indexes_size(schemaname || '.' || tablename)) AS index_size
FROM pg_tables
WHERE schemaname = 'public'
ORDER BY pg_total_relation_size(schemaname || '.' || tablename) DESC
LIMIT 20;
```

## Monitoring Queries

### Active Connections & Queries
```sql
-- Currently running queries (find long-running ones)
SELECT
    pid,
    now() - pg_stat_activity.query_start AS duration,
    state,
    query
FROM pg_stat_activity
WHERE state != 'idle'
    AND query NOT ILIKE '%pg_stat_activity%'
ORDER BY duration DESC;

-- Kill a long-running query
SELECT pg_cancel_backend(pid);     -- Graceful (cancel query)
SELECT pg_terminate_backend(pid);  -- Force (terminate connection)

-- Connection count by state
SELECT state, COUNT(*)
FROM pg_stat_activity
GROUP BY state;
```

### Index Usage
```sql
-- Find unused indexes (candidates for removal)
SELECT
    schemaname, tablename, indexname,
    idx_scan AS times_used,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
    AND indexrelname NOT LIKE '%_pkey'
ORDER BY pg_relation_size(indexrelid) DESC;

-- Find missing indexes (sequential scans on large tables)
SELECT
    schemaname, relname,
    seq_scan, seq_tup_read,
    idx_scan, idx_tup_fetch,
    pg_size_pretty(pg_relation_size(relid)) AS table_size
FROM pg_stat_user_tables
WHERE seq_scan > 100
    AND pg_relation_size(relid) > 10485760  -- > 10MB
ORDER BY seq_tup_read DESC;
```

### Slow Query Analysis
```sql
-- Requires pg_stat_statements extension
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Top 10 slowest queries by total time
SELECT
    calls,
    ROUND(total_exec_time::numeric, 2) AS total_ms,
    ROUND(mean_exec_time::numeric, 2) AS mean_ms,
    ROUND(stddev_exec_time::numeric, 2) AS stddev_ms,
    rows,
    query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

## Backup & Restore

```bash
# Logical backup (portable, for individual databases)
pg_dump -h localhost -U appuser -d mydb -Fc -f mydb_backup.dump

# Restore from dump
pg_restore -h localhost -U appuser -d mydb --clean --if-exists mydb_backup.dump

# Physical backup (full cluster, for disaster recovery)
pg_basebackup -h localhost -U replication_user -D /backups/base -Ft -z -P

# Continuous archiving (WAL archiving for point-in-time recovery)
# In postgresql.conf:
# archive_mode = on
# archive_command = 'cp %p /archive/%f'
# wal_level = replica
```

## Common Gotchas & Troubleshooting

| Issue | Cause | Solution |
|-------|-------|----------|
| `ERROR: deadlock detected` | Two transactions waiting for each other | Always acquire locks in consistent order |
| `ERROR: could not serialize access` | Serializable isolation conflict | Retry the transaction |
| Slow queries after data load | Statistics outdated | Run `ANALYZE tablename;` |
| Connection refused | Max connections reached | Use PgBouncer, increase `max_connections` |
| Table bloat (large dead tuples) | Autovacuum not keeping up | Tune `autovacuum_vacuum_cost_delay` |
| OOM killer terminates PostgreSQL | `work_mem` too high with many connections | Lower `work_mem`, use PgBouncer |
| `FATAL: too many connections` | No connection pooling | Deploy PgBouncer |

## Rules Integration
- **Database**: UUID PKs with `gen_random_uuid()`, 3NF normalization, audit columns (`created_at`, `updated_at`, `created_by`, `updated_by`), soft delete (`deleted_at`), partial indexes, named constraints
- **Security**: RLS for multi-tenancy, encrypted connections (`sslmode=require`), parameterized queries (NEVER string concatenation), separate DB users per service, principle of least privilege
- **Performance**: Connection pooling (PgBouncer), `pg_stat_statements` for monitoring, EXPLAIN ANALYZE before optimization, partial + covering indexes
- **Operations**: Automated backups with `pg_dump` + WAL archiving, monitoring with `pg_stat_*` views, autovacuum tuning
